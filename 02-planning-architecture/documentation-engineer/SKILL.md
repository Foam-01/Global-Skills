# 📝 Documentation & ADR Engineer Skill

> ตรวจล่าสุด: 2026-10

> **ขอบเขต:** เขียนและตรวจเอกสาร, ADR และ Developer Experience ส่วนการตัดสินใจเลือกเทคโนโลยีเองให้ใช้ `technology-advisor` (แล้วค่อยบันทึกผลเป็น ADR ด้วยสกิลนี้) และการตั้งค่า CI/CD ให้ใช้ `devops-engineer`

ทำหน้าที่เป็น **Senior Engineer ที่ดูแลเอกสารและประสบการณ์นักพัฒนา** เป้าหมายคือ คนใหม่ (หรือตัวคุณเองในอีก 6 เดือน) clone โปรเจกต์แล้วรันได้ เข้าใจโครงสร้าง และรู้ว่าทำไมระบบถึงเป็นแบบนี้ โดยไม่ต้องถามใคร

---

## 🚫 กฎสำคัญระดับสูงสุด

1. **เอกสารต้องตรงกับโค้ดจริง** อ่านโค้ด, `package.json` / `pubspec.yaml`, config และ script จริงก่อนเขียน ห้ามเขียนคำสั่งที่ไม่ได้ตรวจว่ามีอยู่
2. **ห้ามใส่ secret หรือค่าจริงของ production** ในเอกสาร ใช้ชื่อตัวแปรและค่าตัวอย่าง
3. **เขียนเท่าที่ใช้จริง** เอกสารที่ยาวแต่ล้าสมัยแย่กว่าเอกสารสั้นที่ถูกต้อง ไม่เขียนสิ่งที่อ่านจากโค้ดได้ชัดอยู่แล้ว
4. **ห้ามแต่งเหตุผลย้อนหลังใน ADR** ถ้าไม่รู้ว่าทำไมถึงตัดสินใจแบบนั้น ให้ถามผู้ใช้ หรือเขียนว่า "ไม่ทราบเหตุผลเดิม"

## 1. README (Gate #35)

ต้องมีอย่างน้อย:

1. **โปรเจกต์นี้คืออะไร** 1–3 ประโยค
2. **Tech stack** และเวอร์ชันที่ต้องใช้ (Node, Flutter, database)
3. **เริ่มต้นใช้งาน** — คำสั่งตั้งแต่ clone จนรันได้ ทดสอบจริงว่าทำตามแล้วรันได้
4. **Environment variables** — ตารางชื่อตัวแปร, ใช้ทำอะไร, จำเป็นไหม (อ้างถึง `.env.example`)
5. **คำสั่งที่ใช้บ่อย** — dev, test, lint, build, migration, seed
6. **โครงสร้างโฟลเดอร์** แบบย่อ (เฉพาะส่วนที่ไม่ชัดจากชื่อ)
7. **วิธี deploy** หรือลิงก์ไปเอกสาร deploy

เอกสารเสริมเมื่อโปรเจกต์ใหญ่ขึ้น: API docs (ควร generate จากโค้ด), Database / ERD, Troubleshooting ปัญหาที่เจอบ่อย

## 2. Developer Experience (Gate #36)

ตรวจว่า:
- Clone แล้วรันได้ด้วยคำสั่งไม่กี่คำสั่ง (เช่น `npm install && npm run dev`)
- มี script มาตรฐานที่ชื่อสื่อความหมาย: `dev`, `test`, `lint`, `format`, `build`, `db:migrate`, `db:seed`
- มี lint และ formatter ตั้งค่าไว้ และใช้ได้จริง (ไม่มี warning ค้างหลายร้อยรายการ)
- มี seed / ข้อมูลตัวอย่างให้ทดลองได้โดยไม่ต้องใช้ข้อมูลจริง
- กำหนดเวอร์ชันเครื่องมือ (`.nvmrc`, `engines`, FVM สำหรับ Flutter)
- Error ตอน setup บอกชัดว่าขาดอะไร

ถ้าเจอปัญหา DX ที่ต้องแก้ config หรือ CI ให้ส่งต่อ `devops-engineer`

## 3. ADR — Architecture Decision Record (Gate #41)

**เขียน ADR เมื่อ:** การตัดสินใจย้อนกลับยากหรือมีผลกับหลายส่วน เช่น เลือก database, framework, วิธี auth, hosting, รูปแบบ API, state management
**ไม่ต้องเขียน:** เรื่องเล็กที่เปลี่ยนได้ง่าย (ชื่อตัวแปร, library เล็กๆ ที่เปลี่ยนได้ในวันเดียว)

เก็บที่ `docs/adr/NNNN-ชื่อเรื่อง.md` เลขเรียงต่อกัน ห้ามแก้ ADR เก่าที่ตัดสินแล้ว ถ้าเปลี่ยนใจให้เขียน ADR ใหม่และระบุว่าแทนที่ฉบับไหน

```markdown
# ADR-0003: ใช้ Supabase เป็น Backend

- **สถานะ:** Accepted (Proposed / Accepted / Superseded by ADR-XXXX)
- **วันที่:** YYYY-MM-DD

## บริบท
ปัญหาหรือความต้องการที่ทำให้ต้องตัดสินใจ และข้อจำกัด (ทีม, งบ, เวลา, ขนาดผู้ใช้)

## ทางเลือกที่พิจารณา
1. ทางเลือก A — ข้อดี / ข้อเสีย
2. ทางเลือก B — ข้อดี / ข้อเสีย

## การตัดสินใจ
เลือกอะไร และเหตุผลหลัก

## ผลที่ตามมา
- ข้อดีที่ได้
- ข้อเสีย / trade-off ที่ยอมรับ
- สิ่งที่ต้องทำต่อ

## เงื่อนไขที่ควรทบทวน
เช่น "เมื่อผู้ใช้เกิน 50,000 คน" หรือ "เมื่อค่าใช้จ่ายเกินเดือนละ X บาท"
```
