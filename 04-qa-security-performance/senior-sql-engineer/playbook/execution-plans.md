# 🗺️ Execution Plan Playbook

> ส่วนหนึ่งของสกิล `senior-sql-engineer` — เปิดเมื่อต้องหาว่า query ช้าเพราะอะไร หรือยืนยันว่าการแก้ได้ผลจริง

## EP-01 — เปิดและอ่าน execution plan (เลิกเดา)

### วิธีเปิด

| Database | Plan จริง (รัน query จริง) | Plan ประเมิน (ไม่รัน) |
|---|---|---|
| SQL Server (SSMS) | **Include Actual Execution Plan** (`Ctrl+M`) แล้วรัน → แท็บ *Execution plan* | Display Estimated Execution Plan (`Ctrl+L`) |
| PostgreSQL / Supabase | `EXPLAIN (ANALYZE, BUFFERS) SELECT …` | `EXPLAIN SELECT …` |

- ⚠️ `EXPLAIN ANALYZE` / Actual plan **รัน query จริง** — กับ `UPDATE` / `DELETE` / `INSERT` ให้ครอบด้วย transaction แล้ว `ROLLBACK` หรือรันบนสำเนาข้อมูล ห้ามรันบน production โดยไม่คิด
- อ่านง่ายขึ้น: PostgreSQL วาง output ที่ explain.dalibo.com หรือ explain.depesz.com
- ใช้ **plan จริง** ทุกครั้งที่ทำได้ เพราะมีจำนวนแถวจริงให้เทียบกับที่ประเมินไว้

### อ่านทิศทางไหน

- SQL Server (แบบกราฟิก): ข้อมูลไหลจาก **ขวาไปซ้าย** — กล่องขวาสุดคือที่อ่านข้อมูลจากตาราง / index ส่วน `SELECT` ซ้ายสุดคือผลลัพธ์ · ความหนาของลูกศร = จำนวนแถวที่ส่งต่อ
- PostgreSQL (ข้อความ): อ่านจาก **บรรทัดที่ย่อหน้าลึกที่สุด** ขึ้นมา

### สิ่งที่ต้องดู (เรียงตามความสำคัญ)

**1. แถวจริง vs แถวที่ประเมิน — สัญญาณที่สำคัญที่สุด**
- SSMS แสดงเป็น `Actual of Estimated (%)` เช่น `34 of 1 (3400%)` = ประเมินไว้ 1 แถว แต่จริงได้ 34 แถว
- PostgreSQL: `rows=` ใน `(cost=… rows=…)` เทียบกับ `(actual … rows=…)`
- ต่างกันมาก (เกิน ~10 เท่า) แปลว่า optimizer ตัดสินใจจากข้อมูลผิด → อาจเลือก join / index ผิดทั้ง plan
- สาเหตุที่พบบ่อย: **statistics เก่า** (`UPDATE STATISTICS` / `ANALYZE`), parameter sniffing (SQL Server), เงื่อนไขหลายคอลัมน์ที่สัมพันธ์กัน, ฟังก์ชันครอบคอลัมน์ (IX-03), table variable

**2. ตัวดำเนินการที่อ่านข้อมูล**

| เห็น | ความหมาย | แย่เสมอไหม |
|---|---|---|
| Table Scan (SQL Server, ตาราง heap) / Clustered Index Scan / Seq Scan (PG) | อ่านทั้งตาราง | **ไม่เสมอ** — ตารางเล็ก หรือ query ต้องการข้อมูลสัดส่วนใหญ่ scan อาจเร็วที่สุด (ดู IX-01) |
| Index Seek / Index Scan (PG) | กระโดดไปเฉพาะช่วงที่ต้องการ | ดีเมื่อได้แถวน้อย แต่ถ้า seek + lookup หลายแสนครั้งอาจแย่กว่า scan |
| Key Lookup / RID Lookup (SQL Server) | กลับไปอ่านตารางจริงทีละแถว | แก้ด้วย covering index (IX-02) เมื่อจำนวนครั้งสูง |
| Index Only Scan (PG) | ตอบจาก index อย่างเดียว | ดี — ถ้า `Heap Fetches` สูง ให้ดูเรื่อง vacuum |

- "Table Scan" ใน SQL Server หมายถึงตารางนั้น **ไม่มี clustered index (heap)** — ตารางหลักในระบบ OLTP ส่วนใหญ่ควรมี clustered index / primary key

**3. คำเตือนในแผน**
- ⚠️ เครื่องหมายเตือนสีเหลือง (SQL Server): implicit conversion (ชนิดข้อมูลไม่ตรง → index ใช้ไม่ได้), sort / hash **spill ลง tempdb** (หน่วยความจำไม่พอ), statistics หาย
- PostgreSQL: `Sort Method: external merge Disk` = sort ไม่พอใน memory, `Rows Removed by Filter` สูงมาก = อ่านทิ้งเยอะ

**4. ต้นทุนและเวลา**
- **`Cost %` เป็นค่าประเมินของ optimizer แม้ในแผนจริง** ไม่ใช่ CPU ที่ใช้จริง ใช้ชี้จุดที่น่าสงสัยได้ แต่ถ้าการประเมินจำนวนแถวผิด (ข้อ 1) Cost % ก็ผิดตาม
- ตัวเลขที่วัดจริง: เวลาต่อกล่อง (SSMS รุ่นใหม่แสดงเช่น `0.464s`), `actual time` (PG), logical reads / buffers (IX-04)

**5. Missing Index (ข้อความสีเขียวใน SSMS)**
- เป็นข้อเสนอแนะอัตโนมัติจาก query เดียว **ห้ามสร้างตามทันที** — มักเสนอ INCLUDE ทุกคอลัมน์ ซ้ำกับ index ที่มีอยู่ และไม่คิดถึงต้นทุนการเขียน ให้พิจารณาตาม IX-01 / IX-02 / IX-06

### ขั้นตอนเมื่อเจอ query ช้า

1. เก็บ actual plan + logical reads / buffers **ก่อนแก้**
2. หาจุดที่แถวจริงต่างจากที่ประเมินมากที่สุด และกล่องที่ใช้เวลา / อ่านข้อมูลมากที่สุด
3. ตั้งสมมติฐาน (เช่น "ไม่มี index ที่ seek ได้", "statistics เก่า", "implicit conversion") แล้วแก้ทีละอย่าง
4. เก็บ plan + ตัวเลข **หลังแก้** แล้วเทียบ — รายงานพร้อม plan ทั้งสองแบบ
5. ตรวจว่าจำนวนแถวที่ได้ **เท่าเดิม**

### ตัวอย่าง (SQL Server, ตาราง `Posts`)

| ก่อนมี index | หลังมี `IX_Posts_Score` |
|---|---|
| `Table Scan [Posts]` Cost 100%, 0.464s, `11919 of 9268 (128%)` | `Index Seek (NonClustered) [Posts].[IX_Posts_Score]`, 0.014s, `36846 of 36846 (100%)` |

- หลังแก้ ตัวเลขประเมินตรงกับของจริง 100% และเปลี่ยนจาก scan เป็น seek — นี่คือหลักฐานที่ควรแนบในรายงาน (ดีกว่าการบอกว่า "เร็วขึ้น X เท่า")
- ระวังเทียบให้ตรง query: ถ้าเงื่อนไขก่อนและหลังไม่เหมือนกัน (จำนวนแถวต่างกัน) ตัวเลขเทียบกันไม่ได้

## EP-02 — แยกกล่องใน plan เป็น 4 กลุ่ม แล้วรู้ว่าต้องดูอะไร

| กลุ่ม | ตัวอย่างกล่อง | คำถามที่ต้องถาม |
|---|---|---|
| **1. ดึงข้อมูล** (Data Access) | Table / Clustered Index Scan, Index Seek, Key Lookup · PG: Seq Scan, Index Scan, Index Only Scan, Bitmap Heap Scan | อ่านแถวมากกว่าที่ต้องใช้ไหม? seek ได้ไหม? lookup กี่ครั้ง? (EP-01, IX-01, IX-02) |
| **2. เชื่อมตาราง** (Joins) | Nested Loops, Hash Match, Merge Join · PG: Nested Loop, Hash Join, Merge Join | ชนิด join เหมาะกับจำนวนแถวจริงไหม? (ตารางด้านล่าง) |
| **3. จัดการข้อมูล** (Operations) | Sort, Filter, Stream / Hash Aggregate, Compute Scalar · PG: Sort, Filter, HashAggregate, GroupAggregate | sort / aggregate ข้อมูลจำนวนมากโดยไม่จำเป็นไหม? กรองช้าเกินไปไหม (อ่านมาเยอะแล้วทิ้ง)? |
| **4. คำเตือน** (Warnings) | ⚠️ สีเหลืองบนกล่อง | ดูรายละเอียดคำเตือน (hover / Properties) แล้วแก้ตามสาเหตุ |

### กลุ่ม 2 — ชนิดของ join

| Join | ทำงานอย่างไร | เหมาะเมื่อ | สัญญาณผิดปกติ |
|---|---|---|---|
| **Nested Loops** | วนแถวของฝั่งนอก แล้วค้นฝั่งในทีละแถว | ฝั่งนอกมีแถว **น้อย** และฝั่งในมี index ให้ seek | ฝั่งนอกจริงมีหลายหมื่น–ล้านแถว (มักเกิดจากประเมินจำนวนแถวต่ำเกินไป) → ทำงานซ้ำมหาศาล |
| **Hash Match / Hash Join** | สร้าง hash table จากฝั่งหนึ่ง แล้วเอาอีกฝั่งมาจับคู่ | ข้อมูล **เยอะ** ทั้งสองฝั่ง ไม่มี index ที่เรียงตรงกัน | ใช้หน่วยความจำ ถ้าไม่พอจะ **spill** ลง tempdb / disk (มีคำเตือน) · เจอกับ query ที่ควรได้แถวน้อย อาจแปลว่าขาด index |
| **Merge Join** | เดินคู่กันบนข้อมูลที่ **เรียงแล้ว** ทั้งสองฝั่ง | ทั้งสองฝั่งเรียงตาม key อยู่แล้ว (เช่น join ด้วย clustered key) | มี Sort ขนาดใหญ่ก่อน merge เพื่อเตรียมข้อมูล |

- ไม่มี join ชนิดไหน "ดี" หรือ "แย่" เสมอ — optimizer เลือกจาก **จำนวนแถวที่ประเมินไว้** ถ้าเลือกผิด สาเหตุส่วนใหญ่คือการประเมินผิด (EP-01 ข้อ 1) ไม่ใช่ชนิด join
- **optimizer ไม่ได้ "สุ่ม" เลือก** — เลือกจากต้นทุนที่คำนวณจากจำนวนแถวที่ประเมินไว้, index ที่มี และข้อมูลเรียงอยู่แล้วหรือไม่ เลือกผิดส่วนใหญ่เพราะประเมินจำนวนแถวผิด ไม่ใช่เพราะไม่มี index อย่างเดียว
- **Merge Join เร็วเฉพาะเมื่อข้อมูลเรียงไว้แล้วทั้งสองฝั่ง** ถ้าต้อง Sort ก่อน ต้นทุน sort อาจกินส่วนต่างหมด · **Hash Match ใช้หน่วยความจำตามขนาดฝั่งที่สร้าง hash table** ไม่ได้ "กิน RAM ดุ" เสมอไป ปัญหาจริงคือเมื่อหน่วยความจำที่จองไว้ไม่พอแล้ว spill
- ตัวอย่างจาก SQL Server (join ได้ 60,855 แถว, ประเมินตรง 100%): Nested Loops 0.134s · Hash Match 0.152s · Merge Join 0.110s — ต่างกันไม่มาก เมื่อการประเมินจำนวนแถวถูกต้อง ชนิด join มักไม่ใช่ต้นเหตุหลัก ส่วนต่างจะใหญ่มากเมื่อ optimizer เลือกจากตัวเลขที่ผิด (เช่น Nested Loops กับข้อมูลที่ประเมินไว้ 1 แถวแต่จริงเป็นล้าน)
- ห้ามบังคับชนิด join ด้วย hint (`OPTION (HASH JOIN)`, `LOOP JOIN`) เป็นทางแก้แรก — แก้ statistics / index / รูป query ก่อน hint ทำให้ plan ตายตัวเมื่อข้อมูลเปลี่ยน

### กลุ่ม 4 — คำเตือนที่พบบ่อย (และสิ่งที่ไม่ใช่คำเตือน)

| คำเตือน | ความหมาย | แก้อย่างไร |
|---|---|---|
| **Type conversion / `CONVERT_IMPLICIT`** | ชนิดข้อมูลของค่าที่เทียบไม่ตรงกับคอลัมน์ (เช่น ส่ง `NVARCHAR` ไปเทียบคอลัมน์ `VARCHAR`) | ให้ชนิดของ parameter ตรงกับคอลัมน์ — บางกรณียัง seek ได้แต่ประเมินจำนวนแถวผิด บางกรณีกลายเป็น scan |
| **Spill to tempdb** (Sort / Hash) | หน่วยความจำที่จองไว้ไม่พอ ต้องเขียนลง disk | แก้การประเมินจำนวนแถว (statistics), ลดข้อมูลที่ต้อง sort, ใส่ index ที่เรียงไว้แล้ว |
| **No Join Predicate** | join ไม่มีเงื่อนไข → cross join (แถวคูณกัน) | มักเป็นบั๊ก — ตรวจเงื่อนไข `ON` |
| **Columns With No Statistics** | ไม่มี statistics ให้ประเมิน | สร้าง / อัปเดต statistics |
| **Residual I/O** (SQL Server รุ่นใหม่) | อ่านแถวจาก index มามากแต่ใช้จริงน้อย | ปรับลำดับคอลัมน์ใน index ให้เงื่อนไขอยู่ใน seek |

- **Missing Index ไม่ใช่คำเตือนสีเหลือง** — เป็นข้อความ **สีเขียว** ด้านบนของ plan และเป็นแค่ข้อเสนอแนะ ห้ามสร้างตามทันที (EP-01 ข้อ 5)
- คำเตือนบางอย่างดูน่ากลัวแต่ไม่กระทบเวลาจริง — ตัดสินจากเวลา / reads ของกล่องนั้นด้วย

### Scan vs Seek — เปรียบเทียบให้เข้าใจง่าย และข้อควรระวัง

- **Scan** = เปิดอ่านหนังสือทีละหน้าเพื่อหาคำ · **Seek** = เปิดสารบัญแล้วพลิกไปหน้านั้นเลย
- **Index Scan ≠ อ่านทั้งตาราง:** Clustered Index Scan / Table Scan อ่านทุกแถวของตาราง แต่ **Nonclustered Index Scan อ่านทุกแถวของ index นั้น** ซึ่งมักเล็กกว่าตารางมาก (มีแค่คอลัมน์ใน index) และ scan ที่มี `TOP` / `LIMIT` อาจหยุดก่อนอ่านครบ
- ตัวอย่างจาก SQL Server (ตาราง `Users`, ได้ ~14,146 แถว): Table Scan 0.070s · Clustered Index Scan 0.103s · Index Seek บน `IX_Users_DisplayName` 0.013s — seek เร็วกว่าชัดเจน แต่เวลาระดับ 0.01–0.1 วินาทีแกว่งได้ตามรอบที่รัน (สังเกตว่า Table Scan ในตัวอย่างเร็วกว่า Clustered Index Scan ทั้งที่อ่านทั้งตารางเหมือนกัน) ให้ยืนยันด้วย logical reads และรันหลายครั้ง (IX-04)

### สรุปวิธีใช้ (ฉบับแก้ไข)

- เจอ **Scan** → ถามก่อนว่า query ต้องการข้อมูลกี่ % ของตาราง ถ้าน้อย ให้หาทาง seek ได้ (index, เงื่อนไขที่ sargable) ถ้ามาก scan อาจถูกต้องแล้ว — **ไม่ใช่ทุก scan ต้องเปลี่ยนเป็น seek**
- เจอ **คำเตือน** → อ่านสาเหตุ แล้วแก้ตามตาราง
- เจอ **Nested Loops กับแถวจำนวนมาก** หรือ **Hash / Sort ที่ spill** → ไปดูการประเมินจำนวนแถวก่อนเสมอ
