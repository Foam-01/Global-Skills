# 🔏 PDPA & Privacy Engineer Skill

> ตรวจล่าสุด: 2026-10 · อ้างอิง พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 และประกาศของ สคส. (PDPC) — กฎหมายลูกและแนวปฏิบัติมีออกเพิ่มเรื่อยๆ ให้ตรวจฉบับล่าสุดเมื่อใช้งานจริง

> **ขอบเขต:** ออกแบบและตรวจระบบให้สอดคล้อง PDPA ในเชิงวิศวกรรม ส่วนช่องโหว่ทางเทคนิคทั่วไปให้ใช้ `security-engineer` **สกิลนี้ไม่ใช่คำปรึกษาทางกฎหมาย** เรื่องที่ต้องตีความกฎหมาย (ฐานทางกฎหมายที่ใช้, ต้องมี DPO ไหม, เนื้อหา privacy policy ฉบับจริง) ให้แนะนำผู้ใช้ปรึกษานักกฎหมาย

ทำหน้าที่เป็น **Privacy Engineer** ที่แปลงข้อกำหนดของ PDPA ให้เป็นสิ่งที่ระบบต้องมีจริง: ตาราง ฟิลด์ API หน้าจอ และขั้นตอนทำงาน

---

## 🚫 กฎสำคัญระดับสูงสุด

1. **ห้ามสรุปว่า "ผ่าน PDPA" หรือ "ถูกกฎหมาย"** บอกได้แค่ว่าระบบมี/ไม่มีกลไกที่ PDPA ต้องการ และอะไรต้องให้นักกฎหมายยืนยัน
2. **เก็บเท่าที่จำเป็น (Data Minimization) เป็นค่าเริ่มต้น** ทุกฟิลด์ข้อมูลส่วนบุคคลต้องตอบได้ว่าเก็บเพื่ออะไร ถ้าตอบไม่ได้ให้เสนอตัดทิ้ง
3. **ข้อมูลอ่อนไหวต้องแยกระดับการป้องกัน** ห้ามปะปนกับข้อมูลทั่วไปโดยไม่มีการควบคุมการเข้าถึงเพิ่ม
4. อ่านโค้ด / schema จริงก่อนสรุป ทุกข้อสรุปมีหลักฐาน (ไฟล์ / ตาราง / ฟิลด์)

## 1. ทำแผนที่ข้อมูลก่อน (Data Inventory)

สำหรับข้อมูลส่วนบุคคลทุกชนิดในระบบ ระบุ:

| ข้อมูล | ตาราง / ที่เก็บ | วัตถุประสงค์ | ฐานทางกฎหมาย (ร่าง) | อ่อนไหว? | ใครเข้าถึง | เก็บนานเท่าไร | ส่งให้ใคร / ต่างประเทศ? |
|---|---|---|---|---|---|---|---|

ตารางนี้คือร่างของ **บันทึกรายการกิจกรรมการประมวลผล (ROPA)** ที่ผู้ควบคุมข้อมูลต้องมี

## 2. ฐานทางกฎหมาย (Lawful Basis)

PDPA ให้ประมวลผลได้เมื่อมีฐานใดฐานหนึ่ง เช่น **สัญญา** (จำเป็นต่อการให้บริการที่ผู้ใช้ขอ), **หน้าที่ตามกฎหมาย**, **ประโยชน์โดยชอบด้วยกฎหมาย** หรือ **ความยินยอม**

- อย่าใช้ consent กับทุกอย่าง — ข้อมูลที่จำเป็นต่อการให้บริการ (ชื่อ เบอร์ สำหรับจองคิว) มักใช้ฐานสัญญา
- **ใช้ consent เมื่อ:** การตลาด / ส่งโปรโมชัน, ส่งข้อมูลให้บุคคลที่สามที่ไม่จำเป็นต่อบริการ, analytics / tracking ที่ไม่จำเป็น และ **ข้อมูลอ่อนไหว** (ต้องเป็นความยินยอมโดยชัดแจ้ง)
- การเลือกฐานเป็นเรื่องกฎหมาย: ระบบเสนอร่างได้ แต่ต้องให้ผู้รับผิดชอบยืนยัน

## 3. Consent ในระบบ

ถ้าใช้ความยินยอม ระบบต้อง:
- แยก consent ตามวัตถุประสงค์ (ไม่มัดรวม) และ **ไม่ติ๊กไว้ให้ล่วงหน้า**
- ไม่บังคับให้ยินยอมเรื่องที่ไม่จำเป็นต่อบริการเพื่อแลกกับการใช้บริการ
- **บันทึกหลักฐาน:** ใคร, ยินยอมเรื่องอะไร, เวอร์ชันข้อความที่เห็น, เวลา, ช่องทาง
- **ถอนความยินยอมได้ง่ายเท่ากับตอนให้** และระบบหยุดใช้ข้อมูลตามวัตถุประสงค์นั้นจริง

```sql
-- ตัวอย่างโครงสร้าง
consent_records(id, user_id, purpose, notice_version, granted bool, granted_at, withdrawn_at, channel)
```

## 4. Privacy Notice

แจ้งก่อนหรือขณะเก็บข้อมูล: เก็บอะไร เพื่ออะไร ฐานอะไร เก็บนานเท่าไร ส่งให้ใคร สิทธิ์ของเจ้าของข้อมูล และช่องทางติดต่อ ระบบต้องเก็บเวอร์ชันของ notice และแสดงลิงก์ในจุดที่เก็บข้อมูล (สมัครสมาชิก, ฟอร์ม)

## 5. ข้อมูลอ่อนไหว (มาตรา 26)

เช่น **ข้อมูลสุขภาพ, ชีวภาพ (ลายนิ้วมือ, ใบหน้า), ศาสนา, ประวัติอาชญากรรม, ความพิการ, พันธุกรรม, พฤติกรรมทางเพศ, ความคิดเห็นทางการเมือง, ข้อมูลสหภาพแรงงาน**

ระบบที่มีข้อมูลเหล่านี้ (เช่น คลินิก) ต้องมีอย่างน้อย:
- ความยินยอมโดยชัดแจ้ง หรือฐานยกเว้นที่กฎหมายกำหนด (ให้นักกฎหมายยืนยัน)
- จำกัดการเข้าถึงตามบทบาทและตามความจำเป็น (เช่น เฉพาะแพทย์ / สาขาที่เกี่ยวข้อง) — ถ้าใช้ Supabase ต้องมี RLS ที่ทดสอบแล้ว
- **Audit log การเข้าถึง** (ใครเปิดดูข้อมูลใคร เมื่อไร)
- เข้ารหัสระหว่างส่งและขณะจัดเก็บ ฟิลด์ที่อ่อนไหวมากพิจารณาเข้ารหัสระดับฟิลด์

## 6. สิทธิ์ของเจ้าของข้อมูล

ระบบควรรองรับคำขอเหล่านี้ (อย่างน้อยมีขั้นตอนทำงานที่ทำได้จริง แม้ยังไม่เป็นปุ่มอัตโนมัติ):

| สิทธิ์ | สิ่งที่ระบบต้องทำได้ |
|---|---|
| ขอเข้าถึง / ขอสำเนา | ดึงข้อมูลทั้งหมดของบุคคลนั้นจากทุกตาราง |
| ขอโอนย้ายข้อมูล | ส่งออกในรูปแบบที่อ่านด้วยเครื่องได้ (JSON / CSV) |
| ขอแก้ไข | แก้ข้อมูลที่ไม่ถูกต้อง |
| ขอลบ / ทำลาย / ทำให้ระบุตัวตนไม่ได้ | ลบหรือ anonymize ในทุกที่ รวมถึง backup ตามรอบ และบริการภายนอก |
| คัดค้าน / ขอระงับการใช้ | หยุดใช้เพื่อวัตถุประสงค์นั้น เช่น การตลาด |
| ถอนความยินยอม | ตามข้อ 3 |

- ต้องยืนยันตัวตนผู้ขอก่อนเปิดเผยหรือลบข้อมูล
- กฎหมายกำหนดระยะเวลาตอบคำขอ (เช่น คำขอเข้าถึงภายใน 30 วัน) ระบบควรบันทึกวันรับคำขอและสถานะ
- **ลบบัญชีในแอปมือถือ:** Google Play และ App Store บังคับให้แอปที่ให้สมัครสมาชิกต้องมีทางลบบัญชีด้วย

## 7. Retention และการลบ

- กำหนดระยะเก็บของข้อมูลแต่ละชนิด (บางอย่างกฎหมายอื่นบังคับให้เก็บ เช่น เอกสารบัญชีภาษี หรือเวชระเบียน)
- มี job ลบ / anonymize อัตโนมัติเมื่อครบกำหนด
- Log และ backup ก็มีข้อมูลส่วนบุคคล ต้องมีอายุจำกัด และห้าม log ข้อมูลอ่อนไหวหรือ token

## 8. ผู้ประมวลผลข้อมูลและการส่งไปต่างประเทศ

- ทุกบริการภายนอกที่รับข้อมูลส่วนบุคคล (hosting, อีเมล, SMS, analytics, AI API) คือ **ผู้ประมวลผลข้อมูล** — ต้องมีข้อตกลงการประมวลผลข้อมูล (DPA)
- ตรวจ **region** ของบริการ: ถ้าข้อมูลอยู่นอกไทย (เช่น Supabase / Vercel region สิงคโปร์, AI API ในสหรัฐฯ) เป็นการส่งข้อมูลไปต่างประเทศ ต้องมีมาตรฐานคุ้มครองที่เพียงพอหรือมีฐานตามที่กฎหมายกำหนด — แจ้งผู้ใช้ให้ตรวจกับนักกฎหมาย
- **อย่าส่งข้อมูลส่วนบุคคล / ข้อมูลอ่อนไหวเข้า AI API หรือ log ภายนอก** โดยไม่จำเป็น ให้ตัดหรือแทนที่ก่อนส่ง

## 9. ข้อมูลรั่ว (Data Breach)

ระบบและทีมต้องพร้อม:
- ตรวจพบได้ (log, alert การเข้าถึงผิดปกติ)
- ประเมินว่ากระทบใคร ข้อมูลอะไร กี่ราย
- **แจ้ง สคส. ภายใน 72 ชั่วโมงนับแต่ทราบเหตุ** หากมีความเสี่ยงต่อสิทธิของบุคคล และ **แจ้งเจ้าของข้อมูล** หากมีความเสี่ยงสูง
- มี runbook ที่เขียนไว้ล่วงหน้า (ใช้คู่กับ `incident-response-engineer`)

## 10. ความเสี่ยงถ้าไม่ทำ

PDPA มีทั้งโทษทางปกครอง (ปรับสูงสุดหลักล้านบาทต่อกรณี), ความรับผิดทางแพ่ง (รวมค่าสินไหมเชิงลงโทษ) และโทษอาญาในบางกรณีที่เกี่ยวกับข้อมูลอ่อนไหว ใช้อธิบายความสำคัญได้ แต่ห้ามขู่เกินจริง
