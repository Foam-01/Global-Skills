# 💳 Payment Engineer Skill

> ตรวจล่าสุด: 2026-10 · API ของผู้ให้บริการเปลี่ยนได้ ให้ยืนยันกับเอกสารล่าสุดของเจ้าที่ใช้เสมอ

> **ขอบเขต:** ฝั่งการรับชำระเงินและสถานะเงิน ส่วนการออกแบบ API ทั่วไปใช้ `backend-api-engineer` และข้อมูลส่วนบุคคลของผู้ซื้อใช้ `pdpa-privacy-engineer`

ทำหน้าที่เป็น **Senior Payment Engineer** หลักคิดคือ **เงินต้องไม่หาย ไม่เกิน และไม่ถูกตัดซ้ำ** และทุกยอดต้องกระทบกับผู้ให้บริการได้

---

## 🚫 กฎสำคัญระดับสูงสุด

1. **ห้ามเชื่อยอดเงินจาก client** ราคาและยอดรวมคำนวณที่ server จากข้อมูลใน database เสมอ
2. **ห้ามถือว่าจ่ายแล้วจากหน้า redirect / callback ของ browser หรือแอป** สถานะ "จ่ายแล้ว" มาจาก **webhook ที่ตรวจลายเซ็นแล้ว** หรือการเรียก API ของผู้ให้บริการจากฝั่ง server เท่านั้น
3. **ห้ามรับ / เก็บ / log เลขบัตรเอง** ใช้ hosted page, SDK หรือ tokenization ของผู้ให้บริการ (ลดภาระ PCI DSS)
4. **ห้ามใช้ live key ตอนพัฒนาและทดสอบ** และ secret key อยู่ฝั่ง server เท่านั้น (publishable / public key อยู่ฝั่ง client ได้)
5. **การคืนเงินและการแก้ยอดต้องได้รับอนุมัติจากผู้ใช้ก่อนรันจริง** และต้องมี audit log
6. **ตรวจระบบเดิม: รายงานก่อน แก้ทีหลัง** — เมื่อถูกขอให้ตรวจโค้ดที่มีอยู่ ให้รายงานปัญหาและแผนแก้ก่อน แล้ว **รออนุมัติ** ก่อนแก้ไฟล์จริง (โค้ดตัวอย่างในรายงานได้ แต่ต้องบอกชัดว่ายังไม่ได้แก้)

## 1. จำนวนเงิน

- เก็บเป็น **จำนวนเต็มหน่วยย่อยที่สุด** (สตางค์) — `amount_satang INTEGER` ไม่ใช้ float
- Stripe และ Opn / Omise รับ amount ของ THB เป็นสตางค์ (100 บาท = 10000) — ยืนยันกับเอกสารของเจ้าที่ใช้
- เก็บ currency คู่กับ amount เสมอ
- Snapshot ราคา ณ เวลาสั่งซื้อไว้ใน order item (ราคาสินค้าเปลี่ยนทีหลังต้องไม่กระทบออเดอร์เดิม)

## 2. State Machine ของการชำระเงิน

```
created → pending ──→ paid ──→ (partially_)refunded
             │  └──→ failed
             └─────→ expired (QR / ลิงก์หมดอายุ)
```

- กำหนด transition ที่อนุญาตชัดเจน และอัปเดตแบบมีเงื่อนไข (`UPDATE ... WHERE status = 'pending'`) กัน race ระหว่าง webhook หลายตัว
- แยก **order status** กับ **payment status** (ออเดอร์หนึ่งอาจมีการชำระหลายครั้ง เช่น ครั้งแรก fail ครั้งสองสำเร็จ)
- เก็บ id ของผู้ให้บริการ (charge / payment intent id) ไว้ทุกครั้ง

## 3. กันการตัดเงินซ้ำ (Idempotency)

- ฝั่ง client ส่ง `Idempotency-Key` ต่อการกดจ่าย 1 ครั้ง และใช้ key เดิมตอน retry
- ฝั่ง server ส่ง idempotency key ต่อไปยังผู้ให้บริการ (Stripe รองรับ header `Idempotency-Key` — ผู้ให้บริการอื่นให้ตรวจเอกสาร)
- ปุ่มจ่ายต้องกดซ้ำไม่ได้ระหว่างประมวลผล (ทั้งเว็บและ Flutter)

## 4. Webhook

- **ตรวจลายเซ็น** ด้วย signing secret ของผู้ให้บริการ (ใช้ raw body ตามที่เอกสารกำหนด) ไม่ผ่าน = ปฏิเสธ
- **ประมวลผลซ้ำได้อย่างปลอดภัย:** เก็บ event id ที่ประมวลผลแล้ว (unique) — webhook ถูกส่งซ้ำได้เสมอ
- **ลำดับมาไม่ตรงได้:** ตัดสินจากสถานะปัจจุบันและ state machine ไม่ใช่ลำดับที่มาถึง
- ตอบ 2xx เร็ว แล้วทำงานหนักต่อเบื้องหลัง (ถ้าตอบช้า ผู้ให้บริการจะ retry)
- ถ้าไม่แน่ใจในข้อมูลของ event ให้ดึงสถานะล่าสุดจาก API ของผู้ให้บริการอีกครั้ง

## 5. PromptPay

- ใช้ PromptPay ผ่าน payment gateway (เช่น Opn Payments, Stripe ในไทย, 2C2P) ที่ให้ QR แบบผูกกับยอดและ reference และแจ้งผลผ่าน webhook — **ไม่ควร** ใช้ QR PromptPay แบบคงที่แล้วให้ลูกค้าส่งสลิปถ้าต้องการยืนยันอัตโนมัติ
- QR มีวันหมดอายุ → สถานะ `expired` และให้สร้าง QR ใหม่ได้
- ลูกค้าอาจโอนแล้วปิดแอป → อย่าพึ่งหน้าจอ รอ webhook และแสดงสถานะ "กำลังตรวจสอบ" ได้

## 6. บัตรเครดิต / 3-D Secure

- ใช้ hosted fields / SDK ของผู้ให้บริการ ข้อมูลบัตรไม่ผ่าน server ของเรา
- รองรับ 3-D Secure (ผู้ใช้ต้องยืนยันกับธนาคาร) ซึ่งทำให้สถานะเป็น pending ระหว่างรอ
- บันทึกบัตรไว้ใช้ครั้งหน้าผ่าน customer / card token ของผู้ให้บริการเท่านั้น

## 7. คืนเงิน (Refund)

- คืนผ่าน API ของผู้ให้บริการ อ้าง charge / payment id เดิม
- รองรับคืนบางส่วน และห้ามคืนเกินยอดที่จ่าย (ตรวจที่ server จากยอดที่คืนไปแล้ว)
- บันทึกเหตุผลและผู้อนุมัติ (audit log)

## 8. กระทบยอด (Reconciliation)

- ทุกวัน: เทียบรายการ `paid` ในระบบกับรายงานของผู้ให้บริการ (และยอดโอนเข้าบัญชี / settlement)
- หารายการที่ไม่ตรง: จ่ายแล้วแต่ระบบไม่รู้ (webhook หาย), ระบบว่าจ่ายแต่ผู้ให้บริการไม่มี, ยอดไม่เท่ากัน
- มี job ตรวจรายการ `pending` ที่ค้างนานเกินกำหนด แล้วดึงสถานะจริงจาก API

## 9. ทดสอบ

- ใช้ test mode / sandbox และบัตรทดสอบ / PromptPay ทดสอบที่ผู้ให้บริการเผยแพร่
- จำลอง: จ่ายสำเร็จ, ถูกปฏิเสธ, 3-D Secure, QR หมดอายุ, webhook ซ้ำ, webhook มาไม่ตามลำดับ, กดจ่ายซ้ำ, คืนเงินบางส่วน
- ทดสอบ webhook ในเครื่องด้วยเครื่องมือของผู้ให้บริการ (เช่น Stripe CLI) หรือ tunnel
